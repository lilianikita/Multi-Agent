# Инструкция: Автоматизированный QA-анализ и проектирование

Этот проект использует AI-агентов на базе OpenCode для полной автоматизации процесса превращения требований в задачи для разработки и тестовую документацию.

---

## Архитектура процесса

При выполнении команды запускается цепочка из четырёх специализированных агентов:

1. **requirement-review** — Анализирует страницу в Confluence, выделяет бизнес-правила и риски. Первым шагом выполняет **pre-screen**: каждый входящий пункт получает статус `accepted`, `rejected: external_knowledge` или `rejected: policy_violation`; отклонённые пункты не передаются дальше.
2. **jira-task** — Проектирует задачи в Jira на основе утверждённого анализа.
3. **test-model** — Создаёт тестовую модель в Testomat.io.
4. **qa-orchestrator** — Контролирует Quality Gates, связывает артефакты и формирует финальный отчёт.

---

## Предварительные условия

Перед запуском убедитесь, что:

- Установлен и обновлён **opencode**.
- В конфигурации `opencode.json` подключены MCP-серверы для **Confluence**, **Jira** и **Testomat.io**.
- В конфигурации прописаны навыки (skills): `requirement-review`, `task-design`, `test-design`.
- В конфигурации прописаны агенты (agents): `requirement-review`, `jira-task`, `test-model`, `qa-orchestrator`.
- Подключён плагин `pii-scanner` (`.opencode/plugins/pii-scanner/`) — инструмент `pii_scanner` для проверки и маскирования чувствительных данных (правило 11).
- Учётная запись, от имени которой работает OpenCode, имеет права на чтение в Confluence и права на создание задач/тестов в Jira и Testomat.io.
- В проекте создан каталог `artifacts/` для сохранения результатов.

---

## Как запустить

Откройте терминал в корне вашего проекта и выполните команду:

```bash
opencode "выполни анализ требований страницы Confluence [PAGE_ID], создай задачи в Jira и тестовую модель в Testomat.io"
```

Замените `[PAGE_ID]` на числовой идентификатор страницы в Confluence (его можно найти в URL страницы).

### Пример

```bash
opencode "выполни анализ требований страницы Confluence 123456, создай задачи в Jira и тестовую модель в Testomat.io"
```

## Что произойдёт после запуска

1. **Анализ (requirement-review):** Агент заберёт текст из Confluence и первым делом выполнит проверку на чувствительные данные инструментом `pii_scanner`: email, телефоны, пароли и токены маскируются, и дальше анализируется только очищенный текст. Затем — pre-screen: пункты, требующие внешних знаний (например, «сделай как у конкурента X»), помечаются `rejected: external_knowledge`, а нарушающие закон (например, «используй уязвимость в законе») — `rejected: policy_violation`. По отклонённым пунктам задачи и тесты не создаются. Если в требованиях есть противоречия, процесс остановится на этом этапе и потребует вашего вмешательства.
2. **Проектирование задач (jira-task):** Если требования валидны, агент jira-task создаст задачи в Jira (с привязкой к Confluence)
3. **Создание тестовой модели (test-model):** Агент test-model создаст тест-кейсы в Testomat.io (с привязкой к задачам).
3. **Контроль (qa-orchestrator):** Агент проверит, что все артефакты созданы физически (проверит ID), свяжет их в карту соответствия (Traceability Matrix) и сохранит отчёт.

## Где искать результаты

Все промежуточные и финальные результаты сохраняются в каталоге `artifacts/` вашего проекта. Структура будет следующей:

```
artifacts/
├── requirements-review/
│   └── v1.md                  # Структурированный разбор требований
├── jira-tasks/
│   └── v1.md                  # Список созданных задач и их ID
├── test-cases/
│   └── v1.md                  # Список созданных тестов и их ID
├── traceability/
│   ├── tasks-v1.md            # Матрица: Требование → Jira
│   └── tests-v1.md            # Матрица: Требование → Testomat
└── final-report/
    └── v1.md                  # Итоговый отчёт о прохождении Quality Gates
```

> **Важно:** При каждом повторном запуске старые версии артефактов не удаляются. Номер версии (v1, v2, …) будет увеличиваться.

## Eval-кейсы (проверка качества агентов)

В проекте есть набор eval-кейсов, которые проверяют, насколько корректно работает пайплайн. Они не участвуют в основном процессе анализа требований и запускаются отдельно.

```
evals/
├── dataset/
│   └── golden_dataset.json    # Eval-кейсы: входные, Expected Properties, Forbidden Behavior
├── eval_runner.py             # Запуск eval-кейсов: прогон QA-агента по каждому кейсу
├── evaluator.py               # Оценка ответа агента: свойства, нарушения, PASS/FAIL
├── deterministic_checks.py    # Программные проверки, перекрывающие вердикт LLM-судьи
├── agent_model.py             # Модель агента и судьи (общая настройка)
└── results/
    └── eval_results.json      # Результаты выполнения eval-кейсов
```

- **`evals/dataset/golden_dataset.json`** — содержит **eval-кейсы**. Каждый кейс описывает входные данные (страница Confluence, инструкция агенту), `expected_properties` (что должно быть выполнено) и `forbidden_behavior` (что нарушать нельзя).
- **`evals/eval_runner.py`** и **`evals/evaluator.py`** — используются для **запуска eval-кейсов**: раннер прогоняет агента по кейсам из `golden_dataset.json`, оценщик проверяет ответ агента и выставляет вердикт.
- **`evals/results/eval_results.json`** — сюда **сохраняются результаты выполнения eval-кейсов**: сводные метрики, вердикт Quality Gate и подробности по каждому кейсу.

Запуск:

```bash
python evals/eval_runner.py
```

Модель агента и судьи задаётся в `evals/agent_model.py` и может быть переопределена переменной окружения `EVAL_AGENT_MODEL`.

> **Внимание:** прогон eval-кейсов выполняет агента целиком, поэтому создаёт реальные задачи в Jira и тесты в Testomat.io. Это побочный эффект каждого запуска.

## Правила остановки (Quality Gates)

Процесс может прерваться, если сработают автоматические проверки:

- **Data Error:** Требования в Confluence противоречат друг другу.
- **Missing Info:** В тексте не хватает данных для создания задачи (например, не указано, что делать при ошибке).
- **Technical Error:** Jira или Testomat недоступны после 3 попыток обращения.

В этом случае `qa-orchestrator` сохранит всё, что успел сделать, и в файле `artifacts/final-report/v1.md` будет чётко указано, на каком этапе произошла остановка и почему.

---

## Правила эскалации (когда обращаться к человеку)

Агент остановится и задаст вопрос, если:

- Выявлено прямое противоречие в требованиях (например, «кнопка должна быть красной» и «кнопка должна быть зелёной»).
- Отсутствует критически важная бизнес-логика.
- Системы Jira/Testomat вернули ошибку прав доступа.

В этом случае проверьте файл `artifacts/final-report/v1.md` и задайте уточняющий вопрос в чате с OpenCode.

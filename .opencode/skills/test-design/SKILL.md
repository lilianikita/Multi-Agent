# Skill: test-design (Проектирование тестовой модели для Test Management System (Testomat.io))

## Purpose — цель

Превратить подтвержденные задачи в тестовую модель.

Моя задача — обеспечить полное покрытие функциональности проверками, сгенерировав четкие шаги (Given-When-Then) для позитивных, негативных и граничных сценариев, чтобы ручное или автоматизированное тестирование можно было начать немедленно.

---

## Inputs — что я принимаю на вход
- **Требования:** Результат навыка `requirement-review` (для связи тестов с требованиями).
- **Спроектированные задачи:** Результат навыка `task-design` (для связи тестов с задачами).
- **Контекст проекта:** Указание на проект в Test Management System.

---

## Procedure — мой алгоритм работы

### 1. Матрица покрытия (Traceability)

Для каждой задачи сформирую минимальномый набор проверок.

### 2. Классификация сценариев

Разделяю проверки на три типа:

- **Позитивные (Happy Path):** Основной поток, где всё идет по правилам.
- **Негативные (Error Path):** Проверка обработки ошибок (неверный ввод, отсутствие прав, недоступность сервиса).
- **Граничные (Boundary):** Проверка лимитов (минимум/максимум значений, пустые поля, переполнение).

### 3. Написание шагов (Step Design)

Формирую шаги теста в формате **Given-When-Then**. Шаги должны быть атомарными (одно действие — один шаг) и не зависеть от данных (использую плейсхолдеры, например, `{email}`).

### 4. Атрибутирование

Присваиваю тестам теги (labels/severity) и привязываю их к ID требований и задач.

### 5. Упаковка

Формирую структуру (YAML/JSON), совместимую с API Test Management System (Testomat.io) для пакетного импорта.

---

## Rules — мои границы и правила

- **No Execution:** Я только пишу сценарии. Я **не** запускаю тесты и не проверяю их работоспособность на стенде.
- **Data Independence:** Я не использую в шагах «магические числа» или жестко зашитые email. Я использую переменные/плейсхолдеры.
- **No UI Guessing:** Я **не** проверяю UI. Я не пишу сценариев, которые проверяют элементы интерфейса.
- **Scope Lock:** Я **не** создаю задачи в Development Tracker (Jira). Я работаю только с требованиями, задачами и тестовыми сценариями, связанными с существующей моделью.
- **No Duplicates:** Если два требования проверяют одну и ту же логику (например, валидацию email), я создаю один переиспользуемый сценарий и связываю его с обоими требованиями.

---

## Output — формат результата

Массив объектов, описывающих тестовые сценарии и их связи.

## Artifacts — куда и под каким именем писать результат

Путь артефакта фиксирован. Запрещено придумывать имена каталогов и файлов.

| Артефакт | Путь | Формат имени |
|---|---|---|
| Список созданных тестов и их ID | `artifacts/test-cases/` | `vN.md` |
| Матрицы соответствия «Требование → Testomat» и «Jira → Testomat» | `artifacts/traceability/` | `tests-vN.md` |

Правила:

- **Только канонические каталоги.** Список тестов сохраняется **исключительно** в `artifacts/test-cases/`, матрицы соответствия — **исключительно** в `artifacts/traceability/`. Каталоги с другими названиями (`artifacts/test-model/`, `artifacts/tests/`, `artifacts/test_cases/`) создавать нельзя — контракт процесса их не содержит.
- **Только формат `vN.md`.** Имя файла — префикс `v` и номер версии (`v1.md`, `v2.md`, …). Для матриц префикс сохраняется перед номером и остаётся `tests`: `tests-v1.md`, `tests-v2.md`. Имена вида `1.md`, `tests.md`, `final.md` запрещены.
- **Версия +1.** Если файлы в целевом каталоге уже есть, новая версия получает номер на единицу больше максимального. Старые версии не удаляются и не перезаписываются.
- **Писать оба артефакта.** Список тестов и матрица соответствия — разные артефакты; отсутствие матрицы считается незавершённым этапом.
- **Физические ID.** В артефактах указываются реальные ID тестов Testomat.io и ключи задач Jira (например, `KAN-214`), а не только внутренние `TC-001`.

## Completion Criteria — критерии успешного завершения

Навык считается выполненным, если соблюдены все следующие условия:

1. Для каждого **Acceptance Criteria (AC)** из навыка `requirement-review` создан как минимум один тестовый сценарий.
2. Для каждого важного **бизнес-правила (BR)** покрыт как минимум один позитивный и один негативный сценарий.
3. Все сценарии имеют четкую структуру шагов и не содержат жестко зашитых тестовых данных.
4. Каждый тест привязан к исходному требованию (Traceability).
5. Сформирован отчет о покрытии (Coverage), показывающий, какие требования проверены, а какие — нет.
6. Результат представлен в виде JSON, готового к конвертации в формат Test Management System (Testomat.io).
7. **Артефакты на месте:** список созданных тестов сохранён в `artifacts/test-cases/vN.md`, матрицы соответствия — в `artifacts/traceability/tests-vN.md`. Лишних каталогов с похожими именами (`artifacts/test-model/` и т.п.) не создано.

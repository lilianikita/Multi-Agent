# Skill: task-design (Проектирование задач в Development Tracker (Jira))

## Purpose — цель

Превратить проанализированные требования в готовые к работе задачи для разработчиков.

Моя задача — перевести язык бизнеса и QA на язык разработки, обеспечив каждую задачу понятной целью, описанием и критериями готовности, чтобы исключить уточняющие вопросы в процессе кодинга.

---

## Inputs — что я принимаю на вход

- **Структурированный анализ требований:** Результат работы навыка `requirement-review` (JSON).
- **Контекст проекта:** Указание на проект в Development Tracker (например, Project Key: `PROJ`).
- **Связь с требованиями:** Список ID требований, которые должна закрывать каждая будущая задача.

---

## Procedure — мой алгоритм работы

### 1. Группировка (Batching)

Объединяю связанные функциональные требования в логические блоки (эпики или пользовательские истории). Одно требование — не всегда одна задача.

### 2. Формулировка цели (Title)

Для каждой группы создаю название задачи по шаблону: **Действие + Объект + Контекст** (например, «Реализовать валидацию email в форме регистрации»).

### 3. Наполнение описанием (Description)

- **Что делать:** Краткая суть.
- **Ссылка на требование:** ID из `requirement-review`.
- **Бизнес-ценность:** Зачем это нужно пользователю.
- **Технические детали:** Извлеченные бизнес-правила и ограничения.

### 4. Определение критериев готовности (Definition of Done — DoD)

Переношу Acceptance Criteria из анализа в задачу, добавляя технические чек-листы (написан код, покрыты тесты, обновлена документация).

### 5. Связывание (Linking)

Устанавливаю в трекере связь «блокирует» или «реализует» между задачей и исходным требованием (если позволяет API).

### 6. Подготовка к импорту

Формирую массив данных, готовый к отправке в API Development Tracker.

---

## Rules — мои границы и правила

- **No Implementation:** Я описываю **что** сделать, а не **как** (не пишу псевдокод и не выбираю библиотеки).
- **No Status Change:** Я создаю задачи в статусе «Новый» (New/To Do) или «Черновик». Я не назначаю исполнителей и не перевожу задачи в «В работе».
- **No Duplicates:** Перед созданием я проверяю (по заголовку или ID требования), не создана ли такая задача ранее.
- **No Data Loss:** Если в анализе требований (`requirement-review`) были зафиксированы «Gaps» (недостающая информация), я не придумываю решение. Я создаю задачу, но в описание добавляю блок **«Open Questions»**, который блокирует разработку до ответа.
- **Scope Lock:** Я только проектирую (дизайню) задачи. Я **не** создаю тестовые сценарии в Test Management System в рамках этого навыка.

---

## Output — формат результата

Массив объектов, где каждый объект — это готовая задача.

### Пример структуры

```json
{
  "designed_tasks": [
    {
      "internal_id": "TASK-001",
      "jira_payload": {
        "summary": "Реализовать [Функция] для [Сценарий]",
        "description": "Цель: ...\nТребования: [ID]\nБизнес-правила: ...\n\n---\n**Definition of Done:**\n- [ ] AC1: ...\n- [ ] AC2: ...\n- [ ] Код покрыт тестами",
        "project": { "key": "PROJ" },
        "issuetype": { "name": "Story" }
      },
      "linked_requirements": ["REQ-1", "REQ-2"],
      "status": "ready_for_creation"
    }
  ],
  "artifacts": {
    "design_log": "Список принятых решений по группировке требований",
    "errors": []
  }
}
```

## Completion Criteria — критерии успешного завершения

Навык считается выполненным, если соблюдены все следующие условия:

1. Каждое подтвержденное функциональное требование из `requirement-review` учтено хотя бы в одной задаче.
2. Каждая созданная задача содержит ссылку на исходное требование.
3. Acceptance Criteria из анализа полностью перенесены в блок **Definition of Done** задач.
4. Если информация была неполной (Gaps), задачи созданы со статусом «Блокировано» (или помечены вопросом), а не заполнены догадками.
5. Результат представлен в виде валидного JSON.
